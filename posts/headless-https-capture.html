Headless HTTPS capture on Windows: inside HTTP Debugger's IPC

A signed capture service, a shared-memory ring, and a root CA. The mechanism is ordinary Windows IPC. The security lesson is what happens when plaintext is one mapping away.

Summary

HTTP Debugger Pro is a Windows HTTP and HTTPS debugger. Its GUI is optional in practice. The capture engine is a Windows service that publishes plaintext transactions through named shared-memory rings. A local client that can open those objects and hold the UI mutex can drive the engine without the GUI and read the traffic.

NetSnitch is a PowerShell implementation of that client. I analyzed the 10.0.0.10 build to answer three questions: how the service exposes capture, how the ring works, and what the design looks like from a defender's seat. The short version is that the protocol is fast, simple, and almost entirely unauthenticated beyond the access control on the named objects.

  • There is no RPC endpoint. The UI and service communicate through six named section channels, a named mutex, and events. The service creates the objects; the UI opens them.
  • The UI mutex is a liveness gate, not an authentication token. I did not find a caller image, signature, PID, or window check in the attach path.
  • The transaction channel is a 128-slot ring with 0x6000-byte slots and a separate state array. The consumer must free slots, or the service stalls in the data path.
  • The service installs its interception CA into LocalMachine\Root from its own code path. The UI sends the command; the service performs the trust-store write.
  • Detection should prioritize root-store changes, kernel service and driver installs, named-object handles, and collector egress. Hash-only detection is weak against a signed, rebuildable stack.

NetSnitch is a diagnostics and research tool. It is not an infostealer. The reason it matters to defenders is that the primitives it uses are the same primitives an infostealer can use. That overlap is the subject of the last third of this post.

Both user-mode binaries are 32-bit, including the service. The driver is 64-bit. That split is normal for a product with a 32-bit control plane and a 64-bit data plane: the service is a broker, and the driver is the component that runs in the kernel. A 64-bit client can map the same 32-bit ring layout; pointer width does not change the record format.

The service image base is 0x400000 with entry point 0x31B49B; the UI shares the base and has entry point 0x3B1723. Both images were compiled on 17 September 2026. The service and UI are Authenticode-signed; the signer subject is DevSecOps, Inc. through an SSL.com code-signing chain. The driver carries a Microsoft Windows Hardware Compatibility Publisher signature, which is a WHQL signature. A policy that only blocks unsigned drivers will not stop this stack.

The driver is a NetFilter SDK WFP driver, not custom HTTP Debugger kernel code. Its version resource names netfilter2.sys, and its PDB path is C:\projects\projectsJ\nfsdk\nfsdk\wfp\driver\msvc\Win8Release\X64\netfilter2.pdb. The service copies it into a drv2\x64 or drv2\win32 directory next to the service and registers it from there. That path is unusual for a signed service and is a useful detection artifact.

The user-mode images do not set DYNAMIC_BASE or GUARD_CF in their PE headers. I did not test exploitability; the observation is useful mainly because it makes static addresses stable and because it is another build fingerprint.

Authorized use

The stack installs a kernel driver and a machine-wide root CA, and it intercepts traffic from other processes. Run it only on systems you own or have written authorization to test. The project is a diagnostics tool, not a covert collection platform.

What this post does not contain

A working arming sequence, selector values, a persistence recipe, or a copy-paste collector deployment. The project repository contains the implementation and usage details. This post covers the mechanism and the detection signal.

The service is the capture engine

The first thing to establish is that the UI is not doing the capturing. The service is a real Windows service. Its ServiceMain is at sub_484440, and its SCM entry point calls StartServiceCtrlDispatcherA with the service name HTTPDebuggerPro. Before that call, it initializes the IPC surface with sub_452470:

The order is the point. The named objects exist before the service reports to the SCM. A client does not have to wait for a UI to create them, and the service does not need the UI to be running in order to own the capture engine. The same binary also handles an /install argument at 0x484646, which is how the service installs itself and its driver.

The service imports CreateServiceA, CreateServiceW, OpenSCManagerA, RegisterServiceCtrlHandlerA, and SetServiceStatus. It can install and manage its own service. The driver side is a WFP callout: the service opens \\.\CtrlSM, loads drv2\x64\netfilter2.sys from its own directory, and uses DeviceIoControl to configure the filter. RTTI in the binary includes NetFilterHelper and NetFilterEventHandler, which is consistent with a C++ wrapper around the driver.

The service does not capture by opening a raw socket and sniffing. It sits in the connection path. The driver redirects matching TCP flows to the service, the service terminates TLS with a locally trusted leaf, re-encrypts the request to the origin, and writes the plaintext request and response records to the transaction ring. That is why the service is the right place to look for plaintext: the decryption happens there, not in the browser.

The UI's WinINET and WinHTTP imports are for its own update and licensing traffic. They are not the capture control channel. The capture control channel is the shared-memory ring.

A service with no RPC

The imports tell the story before any disassembly. The service imports the file-mapping, mutex, and event APIs from KERNEL32. It does not import the RPC runtime, and it does not create a named pipe for the UI. There is no COM server registration in the attach path and no socket listener for control messages. The only IPC primitives are named sections, a mutex, and events.

Strings in the service give the object names. The UI's attach function confirms which ones it opens.

This is a deliberate design choice. A shared-memory ring is a good fit for per-request records: no serialization RPC, no per-record syscall beyond the event, and the consumer can map the data once. It is also a design choice with a security consequence: the service is a broker of plaintext, and the only thing between a local process and that plaintext is the access control on the named objects.

Creating the IPC surface

sub_452470 creates the mutex first, then calls the same helper for each channel. The mutex is created with CreateMutexA and the name Global\HttpDebuggerUiStarted. The channel helper is sub_453B90; it builds a security descriptor and calls CreateFileMappingA with INVALID_HANDLE_VALUE, then maps the section with MapViewOfFile and FILE_MAP_ALL_ACCESS.

INVALID_HANDLE_VALUE means the section is backed by the paging file, not a file on disk. That is why the objects are fast and why they leave no capture file behind. The name is the only handle a client needs.

The transaction channel is built with a capacity argument of 0x80. The consumer header validation in NetSnitch confirms a stride of 0x6000, so the data region is 128 x 0x6000 = 3,145,728 bytes, plus 512 bytes of state. The service also creates a SettingsResult channel; the UI attach function I traced does not open it, which suggests the protocol has more surface than the minimum client uses.

The UI is just another client

The UI attach function is sub_4167A0. It does not call a service API. It opens the mutex with OpenMutexA and MUTEX_ALL_ACCESS, then calls sub_417A90 for each channel.

The mapping helper uses CreateFileMappingA with INVALID_HANDLE_VALUE and FILE_MAP_ALL_ACCESS, just like the service. Because the service created the objects first, this is an open-or-create operation. In the normal startup order, it opens the existing sections.

The mutex deserves attention. The service creates it; the UI opens it with MUTEX_ALL_ACCESS; the client holds it while arming. The name is UiStarted, and the semantics are exactly what the name suggests: the service treats the mutex as evidence that a UI is present. It is not a nonce, a signature, or a proof of image identity. A process that can open the mutex can present the same evidence.

I did not find a caller identity check in this attach path. The service does not compare the client's PID, image path, signer, or window handle. The gate is the object access. That is the central security property of the design, and it is the reason the protocol can be driven by a non-GUI client.

Not a remote bug

This is a local design property. The client needs access to the global named objects. In my test the client ran elevated, and I did not establish whether a standard user can open the same objects on a default install. The DACL on the section is the deciding factor. Treat this as a local trust-boundary question, not an unauthenticated network vulnerability.

The ring, in detail

Each channel is a header mapping and one or more data mappings. The header is a small struct of 32-bit words. The consumer validates it before parsing:

OffsetFieldNotes
0x00CapacityNumber of slots
0x04Write cursorWrapping slot index, not a byte offset
0x08Read cursorWrapping slot index
0x14Capacity mirrorValidated by the consumer
0x18Stride0x6000 in this build
0x1CTotalCapacity multiplied by stride
0x20GenerationProducer generation counter
0x28FlagsRing state flags

The data region is capacity fixed-size slots of 0x6000 bytes, immediately followed by a state array of capacity 4-byte words. The state word for slot i is at total + i * 4. The state machine is only three values:

  • 0: free. The producer may claim the slot.
  • 1: the producer is writing.
  • 2: ready. The consumer may read and then set the slot back to 0.

The producer writes only to a free slot, sets the state to 2, updates the write cursor, and pulses the filled event. The consumer reads a ready slot, copies the record, sets the state back to 0, advances the read cursor, and pulses the available event. The service and the UI are a single-producer, single-consumer pair; the state word is the handshake.

Each record starts with a 16-byte chunk header:

OffsetFieldNotes
0x00Framing wordNonzero
0x04Framing wordNonzero
0x08DPayload length
0x0CDPayload length, duplicate
0x10TagField type
0x14Transaction IDGroups records into one transaction
0x18PayloadD bytes

D excludes the 16-byte header. The payload is a sequence of [u32 length][bytes] fields. The tags I observed are 0 for request metadata and headers, 1 for request body, 2 for response metadata and headers, and 3 for response body. A transaction is several records that share the ID at +0x14.

HTTP/2 is bridged to an HTTP/1-shaped record. The engine writes x-exhdr-method, x-exhdr-authority, x-exhdr-path, and x-exhdr-streamid pseudo-headers. A decoder that only looks for a request line will see HTTP/2 as a set of headers with no method; the pseudo-headers are how the method, authority, and path are recovered.

The ring is bounded, and the producer does not grow it. If the consumer falls behind, the service waits for a free slot and then drops the record. In testing, a full ring produced waits of roughly 500 ms per record, which is enough to stall the user's browsing because the service is in the data path. That is why the consumer contract includes freeing slots, not just reading them. A read-only observer that never sets state 2 back to 0 is not a neutral observer; it eventually becomes a traffic problem.

There is a second subtlety: the request records are short-lived. The service writes the request, pairs it with the response, and reuses the slot. A reader that follows the write cursor and reads each slot once will miss many requests and end up with response-only orphans. The practical fix is to rescan all slots and compare a content signature, which is what NetSnitch does. The request record lives for the network round trip, tens of milliseconds, so a 1 ms scan catches it without pinning a core.

The transaction mapping is not encrypted. It contains the decrypted request and response bytes. The service has already done the TLS work; the ring is the plaintext handoff. That is the whole point of the architecture, and it is why the mapping's DACL matters more than the wire protocol.

The command path and the trust boundary

The command ring uses the same chunk header and a 12-byte command body. The first word is the selector; the next two words are reserved in the records I observed; an optional payload follows. The service dispatches the selector through an internal command table. The exact ordinals are version-specific, and I am not reproducing them here. The public project documentation covers the implementation for researchers who need to reproduce the setup.

The important selectors are the ones that install the CA, build the port rules, apply the rules profile, and complete the user handshake. The order is load-bearing: the CA must be trusted before 443 is intercepted, the rules must be built before they can be applied, and the engine does not publish transactions until the handshake completes. The settings profile is separate: it is pushed over the Settings channel as a length-prefixed XML document. Writing settings.xml to disk is not enough; the service's live profile is set by the IPC push.

The service validates the selector and logs invalid ones. That validation is a protocol check, not an authorization check. Once the record is accepted, the service performs the action with its own token. The client does not need to be the UI, and it does not need to present a certificate. It needs a writable mapping and the mutex.

The result is a local confused-deputy pattern. The service runs with more privilege than the client, but it accepts commands from a client whose only credential is access to the object. If the DACL allows a lower-privileged process to open the command ring, that process can ask the service to install a CA, change the filter rules, or publish plaintext. If the DACL does not, the boundary holds. The protocol does not add a second check.

Installing trust: the CA path

HTTPS interception only works if the client trusts the interception CA. The service handles that itself. The binary imports the CRYPT32 certificate-store APIs and contains the CA name HTTP DEBUGGER CA for DEBUG ONLY and a file name HTTP DEBUGGER CA for DEBUG ONLY 3.cer. The import routine is sub_4DA950.

The function is a general-purpose importer. It takes the certificate bytes, a length, a store name, and a scope flag. The caller passes Root and zero for the scope, which selects LocalMachine. The store provider is the wide-character system-store provider, so the store name is converted to the form that provider expects before the call. The add disposition is CERT_STORE_ADD_USE_EXISTING, so a repeat install updates the existing entry instead of creating duplicates.

The CA is installed by the service, not by the UI. The UI sends the command; the service performs the trust-store write. That is why the root-store event is attributable to the service process, and why a detection that only watches PowerShell will miss the actual trust change.

Once the CA is trusted, the service can mint a leaf for any host it intercepts, present it to the client, and relay the connection to the origin. The client sees a valid chain because the root is in LocalMachine\Root. Certificate pinning and applications that ship their own trust store will fail closed; the interception is not universal. But for the large set of applications that use the Windows trust store and do not pin, the plaintext is available.

The CA outlives the service. The project's uninstall path stops and deletes the service but does not remove the root CA. That is a deliberate choice in the tool and a useful detection opportunity: the trust anchor remains after the capture stack is gone. If you find the CA without the service, you have found a persistence artifact.

What the CA is not

It is not a vulnerability in TLS. It is the normal local trust model doing what it is designed to do. The security question is who can add a root and whether the endpoint notices.

From ring records to a collector

Reading the ring is only half the tool. The other half is turning transient slots into a searchable record. NetSnitch's pump groups records by transaction ID, reconstructs the request line and URL from HTTP/1 or the x-exhdr-* pseudo-headers, inflates gzip or deflate bodies by magic bytes, and waits for a short settle window before emitting a transaction. It filters the collector's own uploads by host so a capture does not feed back into itself.

The agent uploads finished transactions as JSON. When the queue is busy, it coalesces up to 128 batches or 8 MB into one application/x-ndjson POST. The collector parses each line, inserts the whole set in one SQLite transaction, and trims each affected agent to its newest 20,000 rows. WAL mode and synchronous=NORMAL keep the write path cheap; the database is a capture cache, not a ledger.

The web UI is deliberately metadata-first. The list query returns only the columns needed for the row: time, method, URL, host, status, process, user, and body lengths. Expanding a row fetches the full headers and bodies on demand. The search box scans the full stored record, including request and response headers and bodies, plus URL, host, method, status, process, and user. Method, status class, and process filters combine with the search, and the same filter clause is used by paging, the live tail, and the statistics endpoint, so the charts and the grid cannot disagree.

The four pies summarize domain, method, status class, and process. Each pie keeps the top categories and adds a remainder slice, so the percentages add up to the full filtered total. Clicking a slice or a legend entry applies that value as a filter. The delete control removes the agent row and all of its transactions in one transaction, and it requires a session.

This is a reasonable triage design for a single analyst and a handful of agents. It is not a SIEM. The search is a set of SQL LIKE predicates over the stored text, not a tokenized index; at 20,000 rows per agent it is fine, and at millions it will not be. The collector also has no ingest authentication: the login protects the UI, but /api/ingest is open so agents can post without a password. Put the collector behind a VPN or an authenticating proxy, and treat the database as sensitive material.

The agent's uploader has a related weakness: it accepts any TLS certificate for the collector connection, because the capture engine may intercept its own upload. That is a pragmatic lab choice, not a production design. Pin the collector certificate or exempt the collector host from interception if you need the upload channel to be trustworthy.

The infostealer overlap

NetSnitch is a diagnostics tool. It is not an infostealer. It captures full transactions for inspection and sends them to a collector; it does not parse browser credential stores, decrypt browser profiles, or prioritize cookies, tokens, and wallets. The distinction matters for intent, scope, and containment.

The primitives are still the same ones an infostealer needs. That is the uncomfortable part. A credential stealer can use a signed network filter and a locally trusted CA to read authentication traffic after the client decrypts it. It does not have to touch the browser's cookie database, defeat profile encryption, or inject into the browser. It can sit in the connection path and take the plaintext.

  • A signed kernel component in the network path.
  • A user-mode service that brokers plaintext.
  • A root CA that makes interception transparent to the client.
  • A headless control channel that does not need a GUI.
  • A collector or staging point that prioritizes the results.

For an infostealer, the target set is different: login forms, OAuth tokens, session cookies, API keys, cryptocurrency exchange sessions, and anything else that appears in headers or bodies. The collection layer would parse and rank those fields. The network layer would be the same. This is why "it is only a debugger" is not a sufficient security argument. The capability is dual-use, and the endpoint cannot infer intent from a shared-memory read.

The overlap also changes the defensive priority. Browser-specific detections that look for access to the cookie database will miss a network interception path. Disk forensics that recover a browser profile will miss tokens that were captured in transit and never written to disk. The controls that matter are the ones that watch the trust anchor, the driver, the service, and the egress.

Do not over-brand it

Calling every use of a signed capture driver a new generation of stealer is inaccurate and unhelpful. The useful claim is narrower: the same Windows primitives support both authorized diagnostics and credential theft, and the defensive artifacts are shared.

Detection

The detection order should follow the impact. A new root CA is the highest-signal event because it changes the trust decision for every application that uses the machine store. A new kernel service or driver is next. Named-object handles and process ancestry are supporting evidence. Network egress is the last mile, and it is the easiest for an operator to change.

Two queries are worth keeping close. The first checks the root store for the CA by subject. The second checks the service and driver paths. Both are cheap and both run without a vendor agent.

For Sysmon, the high-value events are 6 (driver loaded), 13 (registry value set), and 1 (process creation). The registry path for a machine root certificate is under HKLM\SOFTWARE\Microsoft\SystemCertificates\Root\Certificates. A Sysmon 13 rule on that path will catch the trust change even if the service binary is renamed. Event 6 with ImageLoaded ending in netfilter2.sys catches the driver load; pair it with the file path, because the filename is generic to NetFilter SDK.

Do not rely on the service name alone. It is a string in the binary and in the installer, and an operator can choose a different name. The root-store write and the driver load are harder to rename. The same applies to the named objects: the names are stable in this build, but a different build or a wrapper could change them. The behavior, a process holding a writable section and a UI mutex while a signed service publishes plaintext, is the durable signal.

For prevention, WDAC is a better fit than a hash blocklist, but it has to be an allowlist. The driver is WHQL-signed and the service is signed by a commercial CA, so "block unsigned" does nothing. If the product is not approved in your environment, block the specific service binary and the specific driver by hash or file path, and alert on the root CA. If NetFilter SDK is already approved for a VPN or security product, the driver filename alone will produce false positives; use the service path and the CA subject to disambiguate.

The uninstall gap is worth a separate alert. The project stops and deletes the service but leaves the CA. If the CA appears without the service, or survives a service removal, treat it as a persistence artifact and remove it deliberately. The CA is a machine-wide trust decision; it should not be left behind by a tool cleanup.

Limitations

This is a static analysis of one build, with dynamic testing on Windows 10 and 11 x64. The offsets, selector values, and channel set are build-specific. I did not verify the DACL on every OS version or in every install mode, and I did not establish that a standard user can open the mappings. I did not analyze the CA private-key storage, the driver's WFP callouts, or the service's settings parser in depth. The collector is a lab tool, not a hardened multi-tenant service. No memory-safety vulnerability is claimed here; the finding is architectural.

The binaries are third-party components of HTTP Debugger Pro. Use a licensed copy, and do not redistribute them outside the terms of the vendor's license. The NetSnitch repository is the reference implementation for the client side; this post is the analysis of why it works and what it leaves behind.

What to take away

The interesting part of this stack is not that a debugger can run without its GUI. It is that a signed network service exposes plaintext through a general-purpose IPC surface whose only caller check is object access and a named mutex. That pattern is common in Windows software, and it is exactly the pattern an infostealer can reuse.

The defensive priorities are clear. Watch the root store. Watch kernel service and driver installs, especially from user-writable paths. Watch for processes holding the debugger's named sections without the UI. Watch the egress, but do not make it the first line. Hashes and service names are useful for triage; they are not the control.

NetSnitch is a research tool, not a stealer. The distinction is real, and it should be stated. The detection problem does not depend on the distinction. The primitives are the same, and the endpoint has to notice them.
