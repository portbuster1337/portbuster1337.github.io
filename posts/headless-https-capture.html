Headless HTTPS capture on Windows: a red team view of HTTP Debugger's IPC

A signed SYSTEM service, a shared-memory ring, and a machine-wide root CA. I rebuilt the control channel to learn how an operator can drive the capture engine, and what the same primitives leave behind.

Summary

HTTP Debugger Pro is a Windows HTTP and HTTPS debugger. Its GUI is optional in practice. The capture engine is a Windows service that publishes plaintext transactions through named shared-memory rings. A local client that can open those objects and hold the UI mutex can drive the engine without the GUI and read the traffic.

I look at this stack from an operator's seat. NetSnitch is a PowerShell client I built to answer three questions: how the service exposes capture, how the ring works, and what a headless client has to do to stay in the data path without breaking it. The short version is that the control plane is fast, simple, and almost entirely unauthenticated beyond the access control on the named objects.

  • There is no RPC endpoint. The UI and service communicate through six named section channels, a named mutex, and events. The service creates the objects; the UI opens them.
  • The UI mutex is a liveness gate, not an authentication token. I did not find a caller image, signature, PID, or window check in the attach path.
  • The transaction channel is a 128-slot ring with 0x6000-byte slots and a separate state array. The consumer must free slots, or the service stalls in the data path.
  • The service installs its interception CA into LocalMachine\Root from its own code path. The UI sends the command; the service performs the trust-store write. That is the loudest and most durable part of the stack.
  • The trust boundary is object access, not caller identity. A SYSTEM service executes commands from any client that can open the command mapping. The global namespace, the named mutex, and the uninstaller that leaves the CA behind are design choices, not memory-safety bugs.
  • The ring carries Authorization headers, Cookie values, form bodies, OAuth tokens, and API keys in plaintext. An intrusion operator can stage those records and exfiltrate them over normal HTTPS; no browser profile or cookie database is needed.
  • For a red team, the read path and the command path have different costs. Mapping the transaction channel is quiet but still puts a consumer in the data path. Installing the CA and changing filter rules is more capable and leaves artifacts that outlive the operation.
  • For a blue team, the durable signals are root-store changes, kernel service and driver installs, named-object handles, and collector egress. Hash-only detection is weak against a signed, rebuildable stack.

NetSnitch is a diagnostics and research tool. It is not an infostealer. The reason it matters to an operator is that the primitives it uses are the same primitives an intrusion can reuse. The reason it matters to a blue team is that the artifacts are shared. That overlap is the subject of the last third of this post.

Both user-mode binaries are 32-bit, including the service. The driver is 64-bit. That split is normal for a product with a 32-bit control plane and a 64-bit data plane: the service is a broker, and the driver is the component that runs in the kernel. A 64-bit client can map the same 32-bit ring layout; pointer width does not change the record format.

The service image base is 0x400000 with entry point 0x31B49B; the UI shares the base and has entry point 0x3B1723. Both images were compiled on 17 September 2026. The service and UI are Authenticode-signed; the signer subject is DevSecOps, Inc. through an SSL.com code-signing chain. The driver carries a Microsoft Windows Hardware Compatibility Publisher signature, which is a WHQL signature. A policy that only blocks unsigned drivers will not stop this stack.

The driver is a NetFilter SDK WFP driver, not custom HTTP Debugger kernel code. Its version resource names netfilter2.sys, and its PDB path is C:\projects\projectsJ\nfsdk\nfsdk\wfp\driver\msvc\Win8Release\X64\netfilter2.pdb. The service copies it into a drv2\x64 or drv2\win32 directory next to the service and registers it from there. That path is unusual for a signed service and is a useful detection artifact.

The user-mode images do not set DYNAMIC_BASE or GUARD_CF in their PE headers. I did not test exploitability; the observation is useful mainly because it makes static addresses stable and because it is another build fingerprint.

Authorized use

The stack installs a kernel driver and a machine-wide root CA, and it intercepts traffic from other processes. Run it only on systems you own or have written authorization to test. The project is a diagnostics tool, not a covert collection platform.

What this post does not contain

A working arming sequence, selector values, a persistence recipe, or a copy-paste collector deployment. The project repository contains the implementation and usage details. This post covers the architecture, the reverse engineering, the operational tradeoffs, and the visibility a blue team gets from the same stack.

The service is the capture engine

The first thing an operator has to establish is that the UI is not doing the capturing. The service is a real Windows service. Its ServiceMain is at sub_484440, and its SCM entry point calls StartServiceCtrlDispatcherA with the service name HTTPDebuggerPro. Before that call, it initializes the IPC surface with sub_452470. That order is what makes a headless client possible:

The order is the point. The named objects exist before the service reports to the SCM. A client does not have to wait for a UI to create them, and the service does not need the UI to be running in order to own the capture engine. The same binary also handles an /install argument at 0x484646, which is how the service installs itself and its driver.

The service imports CreateServiceA, CreateServiceW, OpenSCManagerA, RegisterServiceCtrlHandlerA, and SetServiceStatus. It can install and manage its own service. The driver side is a WFP callout: the service opens \\.\CtrlSM, loads drv2\x64\netfilter2.sys from its own directory, and uses DeviceIoControl to configure the filter. RTTI in the binary includes NetFilterHelper and NetFilterEventHandler, which is consistent with a C++ wrapper around the driver.

For a red team, the service is the valuable part of the stack. It holds the driver handle, terminates TLS, and writes the decrypted records. It also performs the privileged commands with its own SYSTEM token. A client that can drive it is not just reading memory; it is asking a SYSTEM process to change the host.

The service does not capture by opening a raw socket and sniffing. It sits in the connection path. The driver redirects matching TCP flows to the service, the service terminates TLS with a locally trusted leaf, re-encrypts the request to the origin, and writes the plaintext request and response records to the transaction ring. That is why the service is the right place to look for plaintext: the decryption happens there, not in the browser.

The UI's WinINET and WinHTTP imports are for its own update and licensing traffic. They are not the capture control channel. The capture control channel is the shared-memory ring.

A service with no RPC

The imports tell the story before any disassembly. The service imports the file-mapping, mutex, and event APIs from KERNEL32. It does not import the RPC runtime, and it does not create a named pipe for the UI. There is no COM server registration in the attach path and no socket listener for control messages. The only IPC primitives are named sections, a mutex, and events.

For an operator, that is a small and stable interface. There is no IDL to recover and no service endpoint to authenticate to. The protocol is a section header, a ring layout, and a set of object names. Strings in the service give the names; the UI's attach function confirms which ones it opens.

This is a deliberate design choice. A shared-memory ring is a good fit for per-request records: no serialization RPC, no per-record syscall beyond the event, and the consumer can map the data once. For an operator, the control surface is the object namespace. For a blue team, the same property means process ancestry and network telemetry may miss the control path entirely; the section and mutex handles are the evidence.

Creating the IPC surface

sub_452470 creates the mutex first, then calls the same helper for each channel. The mutex is created with CreateMutexA and the name Global\HttpDebuggerUiStarted. The channel helper is sub_453B90; it builds a security descriptor and calls CreateFileMappingA with INVALID_HANDLE_VALUE, then maps the section with MapViewOfFile and FILE_MAP_ALL_ACCESS. For an operator, that is a clean map: one mutex, then one helper repeated per channel. For a blue team, the repeated helper is why a single object-name rule covers most of the surface.

INVALID_HANDLE_VALUE means the section is backed by the paging file, not a file on disk. That is why the objects are fast and why they leave no capture file behind. The name is the only handle a client needs. That is convenient for an operator and awkward for attribution: the object is ephemeral, and the name is not proof of who created it.

The transaction channel is built with a capacity argument of 0x80. The consumer header validation in NetSnitch confirms a stride of 0x6000, so the data region is 128 x 0x6000 = 3,145,728 bytes, plus 512 bytes of state. The service also creates a SettingsResult channel; the UI attach function I traced does not open it, which suggests the protocol has more surface than the minimum client uses. A client only needs the transaction channel to read traffic; the extra channels are part of the command and settings path.

The UI is just another client

The UI attach function is sub_4167A0. It is a useful reference implementation for a red team client because it does not call a service API. It opens the mutex with OpenMutexA and MUTEX_ALL_ACCESS, then calls sub_417A90 for each channel.

The mapping helper uses CreateFileMappingA with INVALID_HANDLE_VALUE and FILE_MAP_ALL_ACCESS, just like the service. Because the service created the objects first, this is an open-or-create operation. In the normal startup order, it opens the existing sections.

The mutex deserves attention. The service creates it; the UI opens it with MUTEX_ALL_ACCESS; the client holds it while the engine is active. The name is UiStarted, and the semantics are exactly what the name suggests: the service treats the mutex as evidence that a UI is present. It is not a nonce, a signature, or a proof of image identity. A process that can open the mutex can present the same evidence.

For an operator, this is the difference between needing the vendor's GUI and writing a small client. For a blue team, a process holding the mutex without the UI is a useful anomaly. The mutex is not a strong control, but the mismatch is still a signal.

I did not find a caller identity check in this attach path. The service does not compare the client's PID, image path, signer, or window handle. The gate is the object access. That is the central security property of the design, and it is the reason the protocol can be driven by a non-GUI client. It is also the reason the UI is not a security boundary.

Not a remote bug

This is a local design property. The client needs access to the global named objects. In my test the client ran elevated, and I did not establish whether a standard user can open the same objects on a default install. The DACL on the section is the deciding factor. Treat this as a local trust-boundary question, not an unauthenticated network vulnerability.

The ring, in detail

Each channel is a header mapping and one or more data mappings. The header is a small struct of 32-bit words. A ring is a good target for an operator because one mapping gives you the record layout and one state array gives you the producer-consumer handshake. The consumer validates the header before parsing:

OffsetFieldNotes
0x00CapacityNumber of slots
0x04Write cursorWrapping slot index, not a byte offset
0x08Read cursorWrapping slot index
0x14Capacity mirrorValidated by the consumer
0x18Stride0x6000 in this build
0x1CTotalCapacity multiplied by stride
0x20GenerationProducer generation counter
0x28FlagsRing state flags

The data region is capacity fixed-size slots of 0x6000 bytes, immediately followed by a state array of capacity 4-byte words. The state word for slot i is at total + i * 4. The state machine is only three values:

  • 0: free. The producer may claim the slot.
  • 1: the producer is writing.
  • 2: ready. The consumer may read and then set the slot back to 0.

The producer writes only to a free slot, sets the state to 2, updates the write cursor, and pulses the filled event. The consumer reads a ready slot, copies the record, sets the state back to 0, advances the read cursor, and pulses the available event. The service and the UI are a single-producer, single-consumer pair; the state word is the handshake. For an operator, the important point is that the consumer is part of the system, not a passive observer.

Each record starts with a 16-byte chunk header:

OffsetFieldNotes
0x00Framing wordNonzero
0x04Framing wordNonzero
0x08DPayload length
0x0CDPayload length, duplicate
0x10TagField type
0x14Transaction IDGroups records into one transaction
0x18PayloadD bytes

D excludes the 16-byte header. The payload is a sequence of [u32 length][bytes] fields. The tags I observed are 0 for request metadata and headers, 1 for request body, 2 for response metadata and headers, and 3 for response body. A transaction is several records that share the ID at +0x14.

HTTP/2 is bridged to an HTTP/1-shaped record. The engine writes x-exhdr-method, x-exhdr-authority, x-exhdr-path, and x-exhdr-streamid pseudo-headers. A decoder that only looks for a request line will see HTTP/2 as a set of headers with no method; the pseudo-headers are how the method, authority, and path are recovered.

The ring is bounded, and the producer does not grow it. If the consumer falls behind, the service waits for a free slot and then drops the record. In testing, a full ring produced waits of roughly 500 ms per record, which is enough to stall the user's browsing because the service is in the data path. That is why the consumer contract includes freeing slots, not just reading them. A read-only observer that never sets state 2 back to 0 is not a neutral observer; it eventually becomes a traffic problem.

There is a second subtlety: the request records are short-lived. The service writes the request, pairs it with the response, and reuses the slot. A reader that follows the write cursor and reads each slot once will miss many requests and end up with response-only orphans. The practical fix is to rescan all slots and compare a content signature, which is what NetSnitch does. The request record lives for the network round trip, tens of milliseconds, so a 1 ms scan catches it without pinning a core.

The transaction mapping is not encrypted. It contains the decrypted request and response bytes. The service has already done the TLS work; the ring is the plaintext handoff. That is the whole point of the architecture, and it is why the mapping's DACL matters more than the wire protocol. If you can map it, you can read it. If you cannot, the rest of the protocol does not help.

The command path and the trust boundary

The command ring uses the same chunk header and a 12-byte command body. The first word is the selector; the next two words are reserved in the records I observed; an optional payload follows. The service dispatches the selector through an internal command table. The exact ordinals are version-specific and are not reproduced here. The public project documentation covers the implementation.

The commands that matter are the ones that install the CA, build the port rules, apply the rules profile, and complete the user handshake. The order is load-bearing: the CA must be trusted before 443 is intercepted, the rules must be built before they can be applied, and the engine does not publish transactions until the handshake completes. The settings profile is separate: it is pushed over the Settings channel as a length-prefixed XML document. Writing settings.xml to disk is not enough; the service's live profile is set by the IPC push.

The service validates the selector and logs invalid ones. That validation is a protocol check, not an authorization check. Once the record is accepted, the service performs the action with its own token. The client does not need to be the UI, and it does not need to present a certificate. It needs a writable mapping and the mutex.

The result is a local confused-deputy pattern. The service runs with more privilege than the client, but it accepts commands from a client whose only credential is access to the object. If the DACL allows a lower-privileged process to open the command ring, that process can ask the service to install a CA, change the filter rules, or publish plaintext. If the DACL does not, the boundary holds. The protocol does not add a second check.

For a red team, this is the main tradeoff. The read path is a memory mapping and a consumer loop. The command path is a request to a SYSTEM service to change trust, filter rules, and engine state. The read path is quieter but still puts a consumer in the data path. The command path is more capable but leaves durable artifacts. The objective should decide which one is in scope, not convenience.

Installing trust: the CA path

HTTPS interception only works if the client trusts the interception CA. The service handles that itself. The binary imports the CRYPT32 certificate-store APIs and contains the CA name HTTP DEBUGGER CA for DEBUG ONLY and a file name HTTP DEBUGGER CA for DEBUG ONLY 3.cer. The import routine is sub_4DA950. For an operator, this is the step that turns a network filter into transparent plaintext. For a blue team, it is the most durable artifact in the stack.

The function is a general-purpose importer. It takes the certificate bytes, a length, a store name, and a scope flag. The caller passes Root and zero for the scope, which selects LocalMachine. The store provider is the wide-character system-store provider, so the store name is converted to the form that provider expects before the call. The add disposition is CERT_STORE_ADD_USE_EXISTING, so a repeat install updates the existing entry instead of creating duplicates.

The CA is installed by the service, not by the UI. The UI sends the command; the service performs the trust-store write. A registry or ETW event for that write should show the service process, not the UI, so a blue team should not limit the search to PowerShell or the UI process. An operator should assume that the trust change is visible at the service boundary.

Once the CA is trusted, the service can mint a leaf for any host it intercepts, present it to the client, and relay the connection to the origin. The client sees a valid chain because the root is in LocalMachine\Root. Certificate pinning and applications that ship their own trust store will fail closed; the interception is not universal. But for the large set of applications that use the Windows trust store and do not pin, the plaintext is available.

The CA outlives the service. The project's uninstall path stops and deletes the service but does not remove the root CA. For an operator, that is a cleanup problem and a reason to treat the trust anchor as a host change, not a transient tool artifact. For a blue team, it is a persistence artifact: the trust anchor remains after the capture stack is gone. If you find the CA without the service, you have found a trust-store change that outlived its installer.

What the CA is not

It is not a vulnerability in TLS. It is the normal local trust model doing what it is designed to do. The security question is who can add a root and whether the endpoint notices.

From ring records to a collector

Reading the ring is only half the operator problem. The other half is turning transient slots into a searchable record. NetSnitch's pump groups records by transaction ID, reconstructs the request line and URL from HTTP/1 or the x-exhdr-* pseudo-headers, inflates gzip or deflate bodies by magic bytes, and waits for a short settle window before emitting a transaction. It filters the collector's own uploads by host so a capture does not feed back into itself.

The collector is convenient, but it is also the point where plaintext leaves the host. For a red team, that is a staging and triage decision with its own detection surface. For a blue team, it is the easiest part of the stack to observe from the network and the easiest part for an operator to move.

The agent uploads finished transactions as JSON. When the queue is busy, it coalesces up to 128 batches or 8 MB into one application/x-ndjson POST. The collector parses each line, inserts the whole set in one SQLite transaction, and trims each affected agent to its newest 20,000 rows. WAL mode and synchronous=NORMAL keep the write path cheap; the database is a capture cache, not a ledger.

The web UI is deliberately metadata-first. The list query returns only the columns needed for the row: time, method, URL, host, status, process, user, and body lengths. Expanding a row fetches the full headers and bodies on demand. The search box scans the full stored record, including request and response headers and bodies, plus URL, host, method, status, process, and user. Method, status class, and process filters combine with the search, and the same filter clause is used by paging, the live tail, and the statistics endpoint, so the charts and the grid cannot disagree.

The four pies summarize domain, method, status class, and process. Each pie keeps the top categories and adds a remainder slice, so the percentages add up to the full filtered total. Clicking a slice or a legend entry applies that value as a filter. The delete control removes the agent row and all of its transactions in one transaction, and it requires a session.

For an operator, this is a reasonable triage design for a single analyst and a handful of agents. It is not a SIEM, and it is not hardened. The search is a set of SQL LIKE predicates over the stored text, not a tokenized index; at 20,000 rows per agent it is fine, and at millions it will not be. The collector also has no ingest authentication: the login protects the UI, but /api/ingest is open so agents can post without a password. Put the collector behind a VPN or an authenticating proxy, and treat the database as sensitive material. A staging point that holds full headers and bodies is a credential store whether or not that was the intent.

The agent's uploader has a related weakness: it accepts any TLS certificate for the collector connection, because the capture engine may intercept its own upload. That is a pragmatic lab choice, not a production design. Pin the collector certificate or exempt the collector host from interception if you need the upload channel to be trustworthy. For a red team, that is an operational risk, not a feature.

Where the tradecraft overlaps

NetSnitch is a diagnostics tool. It is not an infostealer. It captures full transactions for inspection and sends them to a collector; it does not parse browser credential stores, decrypt browser profiles, or prioritize cookies, tokens, and wallets. The distinction matters for intent, scope, and containment. It does not change the Windows primitives.

The primitives are the same ones an intrusion operator can reuse. A credential stealer can use a signed network filter and a locally trusted CA to read authentication traffic after the client decrypts it. It does not have to touch the browser's cookie database, defeat profile encryption, or inject into the browser. It can sit in the connection path and take the plaintext.

  • A signed kernel component in the network path.
  • A user-mode service that brokers plaintext.
  • A root CA that makes interception transparent to the client.
  • A headless control channel that does not need a GUI.
  • A collector or staging point that prioritizes the results.

For a red team, the lesson is that network interception is an alternative to browser credential theft. It has different artifacts and different risk. There is no browser profile access and no cookie database to parse, but there is a durable root CA, a kernel driver, and a plaintext staging point. The choice between those paths is an operational tradeoff, not a capability gap.

For an intrusion operator focused on credentials, the target set is different: login forms, OAuth tokens, session cookies, API keys, cryptocurrency exchange sessions, and anything else that appears in headers or bodies. The collection layer would parse and rank those fields. The network layer would be the same. This is why "it is only a debugger" is not a sufficient security argument. The capability is dual-use, and the endpoint cannot infer intent from a shared-memory read.

The credential and cookie problem

The ring is not just a debugging convenience. It carries Authorization headers, Cookie and Set-Cookie values, form bodies, OAuth tokens, and API keys in plaintext. An intrusion operator who can map the ring can select those fields, stage them, and exfiltrate them over ordinary HTTPS. There is no browser profile to decrypt and no cookie database to parse. The result is session hijacking and account takeover material, which is the main reason this design matters beyond debugging.

What HTTP Debugger got wrong

The product is not malware. The problems below are trust-boundary choices that make a dual-use capability easier to abuse. None of them is a memory-safety bug, and several depend on the DACL or directory permissions in a given install; I did not verify those defaults on every supported Windows version.

Design choiceWhy it mattersSafer boundary
The UI is authenticated by a mutex and object access, not caller identity. Any process that can open the mutex and mappings can present the same evidence. The mutex is a liveness flag, not a credential. Bind the channel to an authenticated client identity and verify image, signer, and logon SID.
The SYSTEM service executes command selectors from any client with a writable mapping. A confused-deputy pattern: the client asks the service to install a CA, program WFP rules, or publish plaintext with the service token. Logging invalid selectors is not authorization. Authorize each command against the caller and require explicit consent for trust-store and driver changes.
The CA is machine-wide and labeled DEBUG ONLY. The trust change applies to every user and service that uses the Windows store, and it survives uninstall. A debug-only anchor should not be written to LocalMachine\Root in production. Use a per-user store, require consent, and remove the anchor on uninstall.
The control objects live in Global\ and are not bound to a session or desktop. Cross-session access depends entirely on the DACL. If it is broader than the UI's logon, the service becomes a local privilege boundary bypass. Use a per-session namespace and a DACL restricted to the interactive user and the service SID.
The service loads a WHQL-signed driver from its install directory. A WHQL signature defeats "block unsigned" policy. If the install directory is writable by a lower-privileged user, driver replacement becomes a privilege boundary. Install under a hardened ACL, verify the driver path and signer at load, and run with a restricted token.
The uninstaller removes the service but leaves the CA. The trust anchor outlives the tool. That is a cleanup defect and a persistence artifact for an intrusion operator. Remove the CA on uninstall and provide a verifiable cleanup report.

Taken together, the design gives a local client a path to a SYSTEM trust change and plaintext egress. That is not a remote vulnerability, and a tight DACL may mitigate the worst of it. But the product does not treat the GUI as a security boundary, and it should. The important question is not whether a user can run a debugger; it is whether any process that can open the objects can make the service act for it.

The overlap also changes the defensive priority. Browser-specific detections that look for access to the cookie database will miss a network interception path. Disk forensics that recover a browser profile will miss tokens that were captured in transit and never written to disk. The controls that matter are the ones that watch the trust anchor, the driver, the service, and the egress.

Blue team visibility and operational risk

From an operator's seat, detection is the cost side of the operation. The order below follows impact and durability, not the order of execution. A new root CA is the highest-signal event because it changes the trust decision for every application that uses the machine store. A new kernel service or driver is next. Named-object handles and process ancestry are supporting evidence. Network egress is the last mile, and it is the easiest for an operator to change.

The header is easy to change, so use it as a triage signal, not a blocklist. The collector is the noisiest and most data-rich part of the stack. It should be behind a VPN or authenticating proxy, and the database should be treated as a credential store.
Data Full headers and bodies; authorization headers; cookies DLP; collector database encryption; retention controls. Full plaintext is the objective and the liability. A staging point that is not encrypted or scoped is a worse risk than the capture itself.

Two checks are worth keeping close. The first checks the root store for the CA by subject. The second checks the service and driver paths. Both are cheap and both run without a vendor agent. From an operator's seat, these are the checks to assume will run.

For blue team visibility, the high-value Sysmon events are 6 (driver loaded), 13 (registry value set), and 1 (process creation). The registry path for a machine root certificate is under HKLM\SOFTWARE\Microsoft\SystemCertificates\Root\Certificates. A Sysmon 13 rule on that path will catch the trust change even if the service binary is renamed. Event 6 with ImageLoaded ending in netfilter2.sys catches the driver load; pair it with the file path, because the filename is generic to NetFilter SDK.

Do not rely on the service name alone. It is a string in the binary and in the installer, and an operator can choose a different name. The root-store write and the driver load are harder to rename. The same applies to the named objects: the names are stable in this build, but a different build or a wrapper could change them. The durable signal is the behavior: a process holding a writable section and a UI mutex while a signed service publishes plaintext.

For prevention, WDAC is a better fit than a hash blocklist, but it has to be an allowlist. The driver is WHQL-signed and the service is signed by a commercial CA, so "block unsigned" does nothing. If the product is not approved in your environment, block the specific service binary and the specific driver by hash or file path, and alert on the root CA. If NetFilter SDK is already approved for a VPN or security product, the driver filename alone will produce false positives; use the service path and the CA subject to disambiguate.

The uninstall gap is worth a separate alert. The project stops and deletes the service but leaves the CA. From an operator's seat, that is a cleanup obligation and a reason to plan host cleanup before execution. From a blue team's seat, a CA that appears without the service, or survives a service removal, is a trust-store change that outlived its installer. Treat it deliberately.

Limitations

This is a static analysis of one build, with dynamic testing on Windows 10 and 11 x64 and a collector test in an Any.run Windows VM. The offsets, command ordinals, and channel set are build-specific. I did not verify the DACL on every OS version or in every install mode, and I did not establish that a standard user can open the mappings. I did not analyze the CA private-key storage, the driver's WFP callouts, or the service's settings parser in depth. The collector is a lab tool, not a hardened multi-tenant service. No memory-safety vulnerability is claimed here; the finding is architectural.

The binaries are third-party components of HTTP Debugger Pro. Use a licensed copy, and do not redistribute them outside the terms of the vendor's license. The NetSnitch repository is the reference implementation for the client side. This post is the analysis of how the control plane works, what an operator can reuse, and what the design leaves behind.

What to take away

The interesting part of this stack is not that a debugger can run without its GUI. It is that a signed network service exposes plaintext through a general-purpose IPC surface whose only caller check is object access and a named mutex. For an operator, that is a useful capability: the GUI becomes optional, and the service's token does the privileged work. For a blue team, it is a hard attribution problem because the control path is local object access, not a network protocol.

The exfiltration risk is concrete. The ring already contains authorization headers, cookies, form bodies, and API tokens in plaintext. An intrusion operator does not need browser storage or a cookie database; a selected slice of the ring is enough to hijack sessions and replay API calls. HTTP Debugger's mistake is not that it can capture HTTPS. It is that the privileged service treats object access as authorization, installs a machine-wide CA labeled debug-only, and leaves the anchor behind after uninstall.

The red team lesson is that this is not an exploit chain. It is a control-plane reimplementation. The client is the easy part; the trust anchor and the driver are the expensive parts. The read path is quieter but still puts a consumer in the data path. The command path is more capable but leaves durable artifacts. The objective should decide which one is in scope.

The blue team lesson is to watch the durable changes. Watch the root store. Watch kernel service and driver installs, especially from user-writable paths. Watch for processes holding the debugger's named sections without the UI. Watch the egress, but do not make it the first line. Hashes and service names are useful for triage; they are not the control.

NetSnitch is a research tool, not a stealer. The distinction is real, and it should be stated. The detection problem does not depend on the distinction. The primitives are the same, and the endpoint has to notice them.
